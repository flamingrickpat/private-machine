# A04: Add classification with INVALID fallback

## Summary

This item adds a low-code classification node with LLM selection, declared classes, and a scoped coding-agent recovery path.
It is not implemented by this plan.
Existing workflows do not need to adopt the new node.

Parent: [ordered alpha plan](../index.md).
Dependencies: A02, A03.
Design: [proposed manifest](../workflow-inputs.md#proposed-low-code-manifest).
Policy: [LLM default and optional Laya tests](../model-policy.md).

### Deliver

1. Add the classification phase with exact input or two-pass folder selection, using the LLM by default.
2. Provide declared class routes and the always-present INVALID outcome with a specific coding-agent handler.
3. Expose selection/classification evidence in journals, replay, dry runs, and debugger output.

D04 and D06 confirm INVALID for missing, oversized, malformed, or uncertain input/results.
A fallback actor receives the same question and classes, plus the invalid reason and selected evidence.
Its answer must satisfy the same contract.

### Start from

The pm-workflows protocol, manifest parser, runtime, kernel, extensions, and dry-run analysis.
Choose canonical `kind: classify` spelling against the existing protocol.
Use existing LLM connections for bounded classification and pm-coder for agentic inspection of long or ambiguous inputs.
Keep optional System One connections separate from `agent_model`.
The public decision client remains available without requiring a Laya adapter for this item to pass.

Keep the ordinary coding workflow's transactional behavior.
External-state workflows retain actual effects across classification retries.
There is no Laya usage target.
Laya is limited to simple uses that already pass realistic live-endpoint unit tests.
If enabling a Laya candidate requires expensive effort, omit it and deliver the LLM path.
Do not add tuning or retraining work to make the milestone pass.

### Verify

With the real LLM, select the latest relevant log from mixed folder contents.
Classify the selected captured content.
Inspect both receipts and the exact digest.
Repeat inside a fake filesystem.

Exercise missing files, ambiguous selection, oversized content, invalid responses, and unavailable selected endpoints.
Every condition produces INVALID with a concrete reason.
Verify a scoped coding-agent classification of a long log and an unresolved missing-data case.
Exercise actual agent compaction while retaining the classification instruction, class contract, and decisive log evidence.
Diagnose and repair a failing direct LLM call or lost required context before delivery.

For optional Laya, write realistic synthetic live-endpoint unit tests before enabling it.
Include captured application inputs, near-equal classes, confident wrong answers, and evidence-position changes.
Test selection and classification separately.
Record a failed candidate as rejected and retain the normal LLM path.

Reject missing labels, unknown targets, and absent invalid/fallback destinations.
Include INVALID and its handler in static/dry-run topology.
Prevent infinite fallback recursion.
Run representative existing coding workflows with updated packages.
Run their existing manifests without introducing classification phases or requiring a Laya service.

A05 completes M1 with normal LLM connection wiring through PM.
Use a folder of real test logs with varying names and dates.
Inspect normal routing and coding-agent recovery.
Use a new demonstration workflow for this milestone.

### Handoff

Supply final syntax, LLM context rules, uncertainty policy, live selection/recovery results, demos, and tested dependency locks.
Record whether any optional Laya use passed its tests or remains disabled.
