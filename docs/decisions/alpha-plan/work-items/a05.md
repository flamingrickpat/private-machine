# A05: Make Laya available in PM and evaluate suitable uses

## Summary

This item makes optional decision connections available inside PM and evaluates narrow candidate uses.
Existing workflows keep their current models and execution paths.
It is not implemented by this plan.

Parent: [ordered alpha plan](../index.md).
Dependencies: A01–A04.
Design: [candidate cognitive uses](../decisions.md#candidate-cognitive-uses) and [live cycle](../cognition.md#the-live-cycle).

### Deliver

1. Add optional PM decision connections, lazy service activation, and runtime injection.
2. Provide a new demonstration workflow that uses classification through PM.
3. Evaluate suitable candidates outside existing live workflows and document whether adoption makes sense.

D01 confirms capability availability without forced adoption.
No existing cognitive stage must switch to Laya for this item to pass.
Generative models remain available for classification and interpretive decisions.

### Start from

`runtime/models.py`, `model_activation.py`, `main.py`, and `runtime/workflow_runner.py`.
Add decision configuration without changing current chat defaults.
Reuse A04's demo and supply its optional connection through PM.

A workflow explicitly opts into the decision node.
Unused decision configuration must not launch a service or make a request.
Existing workflows run when no Laya endpoint is configured.

Candidate comparisons use captured inputs and a separate experiment path.
They must not mutate Ghost, dispatch actions, or replace active stage outputs.
Laya answers do not supply generated explanations or arbitrary evidence identifiers.

### Verify

Run existing workflows with Laya absent and verify the same model selection and execution path.
Run the new PM demo with the configured local service.
Inspect selection, classification, INVALID fallback, and service activation receipts.

For suitable candidates, compare reviewed human labels, Laya, and the existing LLM on identical frozen inputs.
Report class errors, uncertainty, fallback rate, latency, and lost explanatory/evidence information.
Use a holdout set.
Conclude that no current stage should change when the measurements support that result.

A measured recommendation is not an automatic migration.
Record any future adoption as an explicit, separately scoped workflow change.
Choose the model according to the task rather than a target percentage of Laya usage.

### Manual test

Complete M1 through the new PM demo.
Run a current conversation or coding workflow with the decision service stopped.
Verify that it retains its current behavior and does not attempt a Laya request.

### Handoff

Supply optional connection configuration, the PM demo, baseline compatibility evidence, candidate results, and tested package locks.
State which candidate uses are suitable and which should remain on an LLM.
