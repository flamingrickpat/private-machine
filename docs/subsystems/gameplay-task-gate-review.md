## Proposed checks with separate inputs

The task already has separate leaves, but every repair still passes through one large planning request.
Splitting final assertions alone does not reduce that request or protect historical attainment.
Use separate decisions with explicit evidence inputs and independently inspectable results.
This is a proposed design, not an implemented replacement gate or new acceptance evidence.
The [implementation guide](gameplay-decision-scopes.md) distinguishes active workflow changes from pending gameplay acceptance.

The [proposed check contract](gameplay-gate-contract-proposal.md) defines decision inputs, dependency migration, result ownership, and validation order.
It preserves the distinction between exact historical recovery proof and fresh recovery from a new incident.

| Check | Required input | Independent result |
| --- | --- | --- |
| Historical proof retention | Exact archived specifications, certificate hashes, actor identities, and recursive dependencies | Original mining, smelting, and crafting proof survives a new recovery incident without repeated material work |
| Iron provenance | Original empty-iron baseline and ordered actual mining, furnace, and crafting receipts | Self-mined ore becomes ingots and a pickaxe; no supplied or village iron counts |
| House structure | Declared geometry and fresh complete cell observations | Floor, walls, roof, door, interior, and supported approach meet the unchanged retained contract |
| Entry and exit | Current body observation, accepted structure, and the two position targets | Separate fresh physical entry and exit succeed in the same body life |
| Home and return | Verified house, durable waypoint, and actual home/outside/home observations | A persisted route matches safe travel in one body life |
| Project integration | The preceding results, original identity bindings, and fresh root observations | All required outcomes remain valid together before publication |

The proof-retention check must precede any instruction to collect more consumed materials.
It must use the exact archived content and all recursive dependencies.
It cannot rewrite certificates or invent acceptance from current inventory.
Historical material attainment and a new recovery incident need distinct node identities.
A changed hazard should invalidate current safety, not erase the provenance of completed crafting.

Each decision needs the current observation, its complete specification, dependency results, and relevant failed attempts.
Preserve the full real Spamuel history and task journals as retrievable evidence with recorded paths and digests.
Record the selected inputs and token count for each request.
Do not substitute a tiny invented persona, a fixed model response, or a fake world.
The final integration check must reject stale structure, a missing pickaxe, lifecycle changes, or mismatched evidence identities.

First establish the smaller protocol boundaries using retained real captures and native model inference.
Then run the remaining physical checks against the retained task and real server.
Finally run an untouched real task to test behavior beyond this repaired history.
Retain the exact M3 constraints until an explicit revised acceptance design replaces them.
Report each check separately so a protocol failure does not become an unsupported judgment about overall model quality.
