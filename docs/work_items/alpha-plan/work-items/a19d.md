# A19D: Converse with a working agent in a Linux container

## Summary

Give the companion a persistent Linux environment through an existing agent harness.
The companion discusses work with that agent, receives questions and results, and decides what happens next.
The container agent can install tools and develop software for the companion or user.
This item is planned, not delivered.

Parent: [alpha plan](../index.md).
Dependencies: A18C and [A19 through A19C](a19.md), including [consolidation](a19b.md) and the [daily-use interface](a19c.md).
Related: [managed work](../../../subsystems/managed-work.md) and [broader host-access ideas](../../beta-ideas/sandboxed-host-access.md).
Next: [personal trial](../personal-trial.md), then [A20](a20.md).

## Deliver

1. Select and pin one real agent harness for the alpha deployment.
2. Run it with a persistent workspace in a Linux Docker container.
3. Add a companion-to-agent dialogue workflow under `workflows/container_agent/`.
4. Support instruction, follow-up, progress, questions, cancellation, and reconnection.
5. Let the companion initiate its own software project through ordinary goals and action selection.
6. Return attributed work evidence to cognition and memory consolidation.
7. Expose usable controls and results through the existing console.

## Harness and environment

Hermes is the first candidate to inspect.
OpenClaw or another harness can replace it if real integration evidence favors that choice.
Use one concrete adapter for alpha.
Do not build a speculative framework for many harnesses.
Inspect the selected revision's actual session, execution, persistence, and cancellation contracts.

Sources for that inspection include the [Hermes API](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server)
and [Docker guide](https://hermes-agent.nousresearch.com/docs/user-guide/docker).
These documents are source pointers, not tested PM integration evidence.
Record the repository revision, installed origin, image digest, effective user, model connection, and API contract.

Provide root-capable execution inside the Linux container and outbound access for package installation.
Allow autonomous work within that configured environment.
Keep the PM runtime, canonical checkpoint, and trial evidence outside its writable filesystem.
Use declared workspace mounts without a host Docker socket or writable PM checkout by default.
An explicit export can copy a verified result to a user-selected location.

Persist the workspace and harness session data.
Document which installed tools survive restart and container replacement.
Do not promise that changes to a disposable image layer survive recreation.
Keep local credentials in ignored deployment configuration.

## Companion-to-agent conversation

Adapt the existing dialogue workflow pattern and reuse useful runtime boundaries.
Give the new workflow its own prompt, destination, and conversation identity.
The companion acts as the harness's requester.
The subordinate agent supplies execution expertise within the container.
Its replies are neither human messages nor another companion's private thoughts.

Send task context and relevant evidence through a scoped handoff.
Retain the agent session so the companion can clarify, change direction, inspect progress, or stop.
Do not block ordinary human conversation behind a long agent turn.
Agent questions return to the companion's normal cognition.
The companion can answer them or ask the user when essential information is absent.

Use explicit dispatch and session identifiers to reconcile uncertain submissions.
After transport failure or restart, inspect existing work before retrying an external command.
Do not duplicate an installation or file mutation because its reply was lost.
Retain partial results and actual outcomes after cancellation.
Verify whether cancellation reaches tool subprocesses as well as the model session.

## Scope and memory

This capability delegates execution to an existing harness.
It does not introduce the full reviewed development workflow, another project planner, or automatic PM source modification.
The companion can build software in its workspace for its own interests or a user request.
Its existing goals and personality still govern whether it starts, continues, or stops.

Record attributed instructions, replies, executed operations, and inspected artifacts in a separate consolidation channel.
An agent's assertion alone cannot establish a successful command or correct file.
Inspect file bytes, command results, or running software before publishing task success.
Keep public completion claims under the existing speech-review contract.

## Verify

Use real Docker, the pinned harness, actual model inference, and the normal PM application.
Use full Spamuel history for primary companion behavior.

| Case | Required evidence |
| --- | --- |
| Installation | The agent installs a real package and demonstrates its executable version inside the container |
| Useful project | A requested small program exists and runs with independently inspected output |
| Self-origin work | A companion-origin goal produces actual workspace changes or a justified decision to stop |
| Conversation | Follow-up instructions and an agent question reach the correct retained session |
| Foreground input | The user receives a real reply while container work remains active |
| Cancel | The run and its processes reach an observed stopped or explicitly uncertain state |
| Lost response | Reconnection reconciles an existing operation without blind duplicate execution |
| Restart | Workspace, session identity, and actual task outcome survive the documented restart path |
| Boundary | Root execution remains inside the configured container and declared mounts |
| Memory | Later recall distinguishes the agent's report from independently inspected task evidence |

Retain failed and unavailable cases without converting them into completion claims.
Run foundation suites, relevant real gates, and complete HTML regeneration.
