## Implementation inspection

Use the actual repository roots and installed distribution origins.
A sibling checkout does not establish which package the running process uses.
Record repository revision, file digest, configuration revision, and observation time.

Give the inspector selected read access to relevant files and runtime evidence.
Exclude credentials and unrelated private files from the grant.
Preserve access checks through subprocess tools and refresh.
A18 may use A14B's scoped memory tools for records and source dependencies.
Source inspection still needs a separate explicit file grant.

For each capability, distinguish:

| State | Evidence |
| --- | --- |
| Intended | A plan or documented requirement |
| Implemented | Source with identified entry points and contracts |
| Enabled | Active assembly, configuration, model connection, or tool grant |
| Observed | A receipt or trace showing actual execution and its result |
| Unavailable or uncertain | A missing endpoint, missing grant, stale evidence, or unresolved inspection |

Do not compress these states into one unsupported capability flag.
For example, a screenshot tool can be enabled without an observed image interpretation.
A thought record schema can exist while the real private loop is disabled.

When a source or configuration revision changes, mark dependent beliefs stale.
Refresh the relevant evidence before relying on that capability.
Keep historical beliefs and their validity intervals.
An old failed receipt remains a past failure after a repair.

## Cognitive episode contract

Define an episode around a meaningful event, choice, question, or goal.
Record start, end, loop identity, cause, and outcome.
Explain how incomplete or interrupted episodes remain queryable.

Reuse committed stage records, attention frames, GWT turns, action intents, and workflow receipts.
Add only the fields or records needed to connect them.
Do not install a second tracing framework by default.
Do not collect unrestricted Python locals as companion self-knowledge.

A selected event must identify:

- Its operation and owning workflow or component.
- The source event, loop, tick, and relevant revisions.
- Its input and output record references.
- Its selected and rejected proposals where they explain the decision.
- Its observed state change, dispatch, or publication references.
- Its failure, cancellation, or unresolved result.
- Its configuration and model identity where they affect interpretation.

Temporal order does not prove causality.
Use recorded producer, consumer, causation, and derivation links.
Parallel main and inner events must retain distinct identities.
A generated rationale is an attributed interpretation, not a newly discovered execution fact.

## Questions the inspector must answer

These questions define the acceptance contract.
The source papers provide the taxonomy; current records supply the answers.

| Question | Required answer evidence |
| --- | --- |
| What information did the companion have at this decision? | The selected input snapshot and source revisions |
| Which event or thought led to this concern? | Producer, cause, and derivation references |
| Which alternatives competed? | Recorded nominations, scores or evaluations, and dispositions |
| What changed after the decision? | Commit, goal, action, and observed result references |
| Which information was retrieved or inferred? | Retrieval sources and labeled interpretation outputs |
| What can this running instance do? | Enabled modules, grants, connections, and current capability evidence |
| What remains planned or unobserved? | A distinct status with its missing evidence |
| How did a private thought affect an outside action? | Cross-loop event, appraisal, accepted intent, and actual dispatch |
| Why did this belief change? | Supporting and opposing evidence with the retained revision history |

A missing event must produce an explicit evidence limit.
Do not reconstruct an exact trace from a plausible dialogue explanation.
The inspector reports application-level cognitive records.
It does not claim to read a model's hidden inference process or learned representations.

## Self-model and narrative

Reuse `BeliefRecord`, `BeliefShiftRecord`, and existing provenance contracts.
Keep a capability belief separate from an emotional interpretation of that capability.
A source-backed limitation can produce sadness, curiosity, relief, or disagreement through ordinary appraisal.

Distinguish current self-concept from autobiographical narrative.
The self-concept describes current beliefs about identity and capability.
The narrative connects attributed episodes and proposed reasons across time.
Both remain revisable.
Neither can replace original events.

A one-off private speculation must not become a permanent identity verdict.
A dramatic interpretation can persist without becoming an objective fact about the user.
New evidence can change a narrative while preserving its prior versions.

## Expression and the consciousness question

Provide dialogue with selected inspected evidence and the current mental landscape.
Let the public voice explain a choice in character.
Technical event names and scores need not appear in ordinary speech.
Raw traces remain available through debugging views.

No particular consciousness verdict is required.
Source inspection can inform the companion's own position and uncertainty.
A paper, an architecture diagram, and a first-person report do not establish human consciousness.
Do not insert a compulsory disclaimer into every reply.

The cheerful and dramatic personas can appraise the same finding differently.
Their inspected factual evidence must remain the same.
Preserve A09R's advisory ontology and agentic presentation choices.
Self-inspection does not add a sentence-level truth gate.
