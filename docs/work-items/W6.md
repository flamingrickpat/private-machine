## Managed-run table

`ManagedRunReceipt` is stored verbatim in `Ghost.managed_runs`, so it survives
checkpoints. `Ghost.from_checkpoint` marks a run that was `accepted`,
`running`, or `waiting_for_input` as `interrupted`; a run that already reached
a terminal state keeps it.

Each receipt holds run ID, originating action ID, workflow name, parent
correlation, state, latest event, artifact location, instructions, revision,
outstanding question ID, answer, request IDs, evidence, and timestamps. The
states are `accepted`, `running`, `waiting_for_input`, `completed`, `failed`,
`cancelled`, and `interrupted`.

`ManagedRunSupervisor.start` persists the accepted identity **before** it
starts the worker. A repeated action ID returns the original receipt and never
launches a second worker. An unknown workflow produces an explicit `failed`
receipt. `update` queues one instruction revision and reuses it for a duplicate
request ID. `terminate` sets the run's code-owned cancellation signal; it never
edits a file. `answer` delivers a correlated answer and resumes a suspended run
with its current instructions.

A real task folder is the working target. Files written before cancellation
remain on disk after the run is `cancelled`.

## SelfManagement, Assistant, steward, consolidation

- `workflows/self_management` maps one typed action into one operation and
  calls the shared functions. A refused operation becomes a typed rejected
  report, never an invented success.
- `workflows/dialogue_assistant` is a separate message contract: a system
  persona with the private ontology, the preserved prior transcript, then the
  current input. A Python role runs the model's tool calls, appends their real
  results, and returns one final utterance. A tool is denied unless it is in
  the run's grant. A management claim in the final text is rejected when no
  executed receipt supports it.
- `runtime/steward` is dormant by default. While dormant it refuses every
  operation and changes nothing. An active status report names its observation
  time and the committed evidence it read. An instruction change is queued for
  the next declared safe boundary and returns the request ID and applied
  revision. Termination is code-only.
- `runtime/consolidation` reads the real task files, hashes them, converts the
  outcome, observations, and experience into typed features whose metadata
  names the run and evidence, and records one consolidation receipt keyed by
  the run and inventory hash. Repeating the request returns the original
  receipt. A changed inventory produces a new receipt without disturbing the
  first.

## Bus wiring

`build_app` constructs one `ManagedRunSupervisor`, one `Consolidator`, and one
dormant `Steward`. The supervisor emits `workflow.question` when a run
suspends and `workflow.event` for other lifecycle events. `MainCogLoop` accepts
`workflow.question` and `workflow.event` and creates a stimulus feature for
each. A terminal run triggers evidence-backed consolidation through the
supervisor's terminal hook.

The real application modules are `main_cog`, `dialogue` (Story), `assistant`,
and `self_management`; the steward module is added on the real path and starts
dormant. The shared management functions are also registered on a FastMCP
server, and a direct test performs a real MCP round trip.

## What changed during implementation

The kernel rejects `mcp_servers` for a Python-role workflow
(`capability_unenforceable`). Assistant dialogue therefore executes the same
scoped functions directly; the same functions are registered on a FastMCP
server and a separate direct test proves the MCP round trip. The verification
rule is unchanged: a claim requires an executed receipt.

## Remaining limits

- Assistant tool execution uses the shared Python functions, not a per-call
  MCP connection, because the kernel forbids MCP capability declarations for
  Python roles. The functions are MCP-exposed and tested.
- The consolidation converts text artifacts into `Feature` records. Structured
  `WorldPlaceKnoxel` / `WorldObjectKnoxel` / image evidence belongs to W8.
- The steward has a domain object and workflow but the running application
  keeps it dormant; no schedule activates it yet.
- The action-selection `depends_on` labels remain model-written workflow names;
  the parent still assigns durable `action-<index>` ids.
- The Story companion-thought follow-up from W5 is unchanged.
