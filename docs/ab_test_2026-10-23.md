# An A/B run of private-machine against another companion architecture (2026-10-23)

Written for the private-machine author by the SCAIL project. Docs only. We built a bench that drives two companion architectures through the same simulated days and has blind judges compare them. One arm was private-machine (fork: sinsforeal/private-machine, branches `bz/parm-patch` and `bz/pmem`, based on upstream e338fbf). We are sharing what we saw because, as far as we know, private-machine has not been run head to head against another design, and some of what we found is cheap to fix.

## What we ran

- Two arms, same model for every call: deepseek-v4.1-flash-1017 (served by Surplus), through one OpenAI-compatible gateway that logs every call.
- Same character card, same per-day environment script (lectures, part-time job, group chat), same simulated user. The simulated user is a model with a style profile; it improvises against her replies, so his lines differ between arms.
- Stepped virtual time: the harness owns the clock and advances each arm in steps; private-machine's own loops run at their native cadence in virtual time.
- Blind judges (Claude Sonnet), one call per criterion per pass, two passes with labels swapped, calibrated on planted defects. Criteria: answers him, her own life, character fidelity, natural language, non-repetition, grounded claims, frame integrity (two more, memory continuity and emotional arc, need 2+ days and were left out).

## Result

One character (an English-speaking university student), the first 10.7 virtual hours of one day:
- The other arm won 4 criteria (grounded claims 4.0 vs 1.0, non-repetition 3.0 vs 1.0, natural language 4.0 vs 2.5, character fidelity 3.5 vs 2.0).
- private-machine won frame integrity (4.5 vs 2.5); 2 criteria split.
- Cost and time for that window: private-machine 3,250 chat calls plus 4,921 embedding calls, 71 M prompt tokens, 7.7 h wall. The other arm used 278 calls and 1.1 M tokens for the whole day.

## This is not a fair comparison

Please read the result with these in mind:
- One day, one seed, one character judged, and only 10.7 virtual hours of it. We stopped the run for memory (below). The second character's private-machine run stalled after 40 virtual minutes and could not be rerun on our 32 GB machine.
- private-machine is built for real time. Stepping it in virtual time runs its 30-second loop back to back, so wall-clock cost here is partly our frame.
- Your prompts were not tuned for deepseek. The host (Surplus) mishandles a trailing assistant message (prefill): it starts a fresh turn and leaks template tokens. We folded the prefill into the user turn at the gateway before this run; earlier runs were hurt by it.
- We patched the harness side (two "fairness patches", listed in the fork's harness/PR_NOTES.md) and added a control layer. We tried not to touch cognition, but any harness is a change.
- The rubric and judges are ours, and the criteria come from our own past failures.

## What we saw in private-machine

Quality, from the transcript and the judges:
- Lines are livelier and wittier than the other arm's, and frame integrity was clean of markup and stamps.
- It sent a message every 10 virtual minutes for about 3 hours while the user had said he was asleep, with no sense of his availability.
- One message came back near-verbatim three times in 30 virtual minutes. Your own notes name this (A19: no codelet notices the repetition).
- It invented: the card says university, the replies mention shoe lockers and walking to school; it sent lines from other people's conversations; plans changed without a cause.
- It sometimes wrote about the user in the third person while talking to him.
- Likely source of the invention: the generator is a story continuation (an assistant prefill ending in an open quote). The model writes a whole scene, often 20 to 40 lines including the user's turns ("User says: ..."), and a later line is taken. A chat-form generator (her lines only, with the world's events labelled) avoided this on the other arm.
- Its plan text ("re-ask the old question") sometimes outweighed the user's new line.

Speed, from the gateway log (one call record per model call):
- About 304 chat calls per virtual hour, prompts of 14k to 32k tokens.
- Calls run one after another: summed model latency 7.37 h vs 7.7 h wall.
- Where the 7.37 h went: structured cognition stages 5.64 h on 2,203 calls (codelet target selection alone 642 calls, 110 min; memories 127 calls at about 32k tokens each), pm-coder tool loops 1.32 h on 889 calls, the private trigger, thought and integration stages 0.32 h, the messages she actually sent 52 calls and about 5 min.
- The private loop runs every 30 virtual seconds whether or not anything happened.
- Each memory commit re-serializes the whole ghost (43 MB after one day) and keeps rolling backups (about 110 files of that size in one day).

Memory:
- The arm process grew about 0.9 GB per virtual hour: 9.7 GB working set, 12.3 GB private at 10.7 virtual hours, while the ghost itself was under 0.2 GB. A full day projects to about 15 GB.
- Likely cause (unverified, offline probe only): the FastMCP tool registry built per codelet-agent run keeps bound methods of that run's MemoryReadSession alive inside pydantic validators, so each session, and the memory snapshot it holds (about 22 MB at 520 records), outlives its run. Pointers: workflows/main_cognition/codelet_agent.py:104-115, pm/host/mcp_listeners.py:153, pm/memory/agent_tools.py (MemoryReadSession.close). Our WIP patch drops the session's data on close; branch `bz/pmem`, commit 542143f, probe harness/measure_leak.py. Not verified in a live run.
- pm-coder sessions and prompt logs are written under the user's home cache directory regardless of the configured run home.

## Suggestions, if useful

1. Break the per-run reference that keeps MemoryReadSession alive (or clear it on close), then re-measure memory over a long run.
2. Gate the private loop on change (a new percept, an elapsed real interval with something pending) instead of running every stage every 30 s.
3. Run independent stages concurrently where the pipeline allows; latency is the wall time today.
4. Consider a chat-form generator, or a stop at the closing quote plus taking the first spoken line, to stop invented scenes and user turns.
5. A repetition check against her last messages before sending.
6. Write checkpoints incrementally, or less often than every commit.
7. Keep pm-coder and prompt-log paths under the configured home.

We are glad to share the harness, the judges and the raw logs of these runs if you want to reproduce or contest any of this.
